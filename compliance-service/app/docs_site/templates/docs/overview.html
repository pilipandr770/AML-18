How AML+18 fits into your product

Short answer: your developers call our API. You do not give us access to your systems or to your own API.

Your backend

A customer signs up or a deposit arrives.

→

AML+18 API

Sanctions lists, address match, on-chain check, AI review.

→

Decision + reasons

accepted, review or rejected. You act on it.

The five steps

  1. Register a project at /developer/signup. You receive an API key, shown once; store it in your secrets manager. On the hosted service a new project is reviewed and activated by the operator (usually within one working day). Until then the key returns 401.
  2. Call the API from your backend, never from a browser or mobile app (the key is a secret). See the Quickstart.
  3. Act on the decision in your own system: hold the deposit, ask for more information, or proceed.
  4. Optional: owner dashboard. Open /owner/register with your API key, set a password and enrol an authenticator app. You can then read every explanation, approve held cases, set the policy and download reports.
  5. Optional: OPERATE mode. Give the agent permission to send signed instructions to your webhook URL, inside limits you set. See The AI agent and webhooks.
Which integration do I need?
Onboarding customers or running a name check: POST /screening/check-name.
Checking a wallet address before crediting or paying out: POST /screening/check-address.
Reviewing every incoming transfer with explanations: POST /agent/transfers (includes the checks above).
Proving a customer controls a wallet, or 18+ checks: /wallet-ownership/*, /age-verify/*.

What you get back

  • accepted – no match worth acting on.
  • review – a possible match; a human must look. We show the list entry, the score and the reasons.
  • rejected – an exact hit (for example a sanctioned wallet address). Never released automatically; a human confirms.

Data and safety in one paragraph

Every decision is written to an append-only, hash-chained journal. The AI model can only raise caution: a deterministic sanctions floor and a policy engine written as ordinary code sit between the model and any action. Text from counterparties (names, memos) is treated as untrusted data. The agent holds no keys and cannot move funds. Early software, testnet and mock ledger only for on-chain checks, not legal advice.
