Going live checklist

AML+18 is early software in a pilot programme. Work through this list with us before you rely on it.

Before you connect

  • ☐ Registered a project and received the API key (stored in a secrets manager, not in code).
  • ☐ Project activated (a test call returns 200/201, not 401).
  • ☐ Jurisdiction profile agreed with us: US (OFAC) or EU (EU list + OFAC). Default is EU.
  • ☐ Counsel has reviewed which duties apply to you. AML+18 is a tool, not legal advice, and does not encode reporting duties.

Integration

  • ☐ Calls come from your server, never from browser or app code.
  • ☐ Timeouts set (we suggest 30 s) and retries with backoff. On error or timeout the item is treated as not cleared.
  • ☐ tx_hash and external_ref sent on every transfer (idempotent retries).
  • ☐ Anything other than auto_cleared is held in your system until a human decides.
  • ☐ review and rejected results reach a person (email, ticket, chat), with the case link.
  • ☐ Sender name, country and address sent whenever you have them (more data means fewer false alarms).

Owner dashboard

  • ☐ Owner account created with an authenticator app; recovery of the authenticator is your responsibility.
  • ☐ Policy set explicitly (an empty policy denies every automated operation).
  • ☐ Journal integrity check shows OK.
  • ☐ Someone is assigned to the Approvals queue and knows the response time you promise customers.

Before enabling OPERATE mode

  • ☐ Webhook endpoint verifies the HMAC signature and the timestamp, and is idempotent.
  • ☐ Webhook secret stored securely (shown once).
  • ☐ Limits set low first (max_amount_per_operation, daily_cap); run MONITOR for at least two weeks and compare recommendations with your own decisions.
  • ☐ Everyone knows where the kill switch is.

Known limits

  • On-chain verification works on testnet (Sepolia) and a mock ledger only. No mainnet yet.
  • Name screening is fuzzy by nature: expect review results that a human clears.
  • No formal certification or audit yet.
